# Регрессионный набор GUI-тестов 1С (web-test test, Allure 3)

Как из разовых GUI-сценариев сделать постоянный процесс: набор тестов на
базу, прогон одной командой после загрузки изменений, отчет, разбор падений.
Движок — режим `test` навыка `web-test` из [cc-1c-skills](https://github.com/Nikolay-Shirokov/cc-1c-skills)
(Playwright поверх веб-клиента). Грабли самого веб-клиента — в
[соседней статье](gotchas.md),
приемы — в [рецептах](recipes.md).

## Разовый сценарий и регрессионный тест — разные режимы

| | `run` / `exec` | `test` |
|---|---|---|
| Файл | произвольный `.js`, код выполняется как тело функции | ES-модуль `*.test.mjs` с `export default async function(ctx)` |
| API | глобальные функции (`clickElement(...)`) | в `ctx` (`ctx.clickElement(...)`) + `step`, `assert`, `log` |
| Импорт общих хелперов | нет (только склейкой файлов) | обычный `import` |
| Отчет | JSON одного прогона | сводка, JSON / JUnit / Allure, скриншот и видео падения по каждому тесту |
| Для чего | разведка формы, разовая проверка | проверка, которая должна жить дальше и гоняться после каждой правки |

Правило: **разведка — в `exec`/`run`, результат разведки — тестом в наборе**.

## Структура набора

```
<набор базы>/
  webtest.config.mjs        url, timeout, retries, screenshot, severity
  _hooks.mjs                prepare()/cleanup() - подготовка стенда
  _allure/categories.json   классы падений
  01-вход/01-открытие-базы.test.mjs
  02-<функция>/01-<сценарий>.test.mjs
```

- Файлы и папки, начинающиеся с `_` или `.`, в обнаружение тестов не
  попадают — туда кладут хуки, конфиг отчета, общие библиотеки.
- Порядок — по алфавиту полного пути, поэтому номера: вход → справочники →
  документы → отчеты → процессы.
- `webtest.config.mjs` и `_hooks.mjs` берутся **из корня набора**, даже если
  запущен один файл из подпапки: движок поднимается вверх до конфига.
- URL в конфиге можно не задавать и передавать `--url=` из профиля базы —
  тогда адрес живет в одном месте.

## Тест

```js
import { stamp, findListRow, markForDeletion } from '../../_lib/1c-helpers.mjs';

export const name = 'Создание контрагента';    // по-русски: попадает в отчет
export const tags = ['контрагенты'];
export const timeout = 120000;                  // по умолчанию 30 с - мало для документов

const TITLE = stamp('GUI-тест');

export default async function(ctx) {
  const { navigateLink, clickElement, fillFields, assert, step } = ctx;
  await step('Создать элемент', async () => { /* ... */ });
  await step('Элемент виден в списке', async () => {
    assert.ok(await findListRow(ctx, TITLE, 'Наименование'), 'Нет в списке');
  });
  await step('Убрать за собой', async () => { await markForDeletion(ctx, TITLE, 'Наименование'); });
}
```

Хелперы в режиме `test` принимают `ctx` первым аргументом: глобальных
функций браузера здесь нет.

## Грабли, найденные при построении процесса

### 1. Уборка в `teardown` не успевает: лимит 15 секунд

`teardown` выполняется всегда, даже при падении теста, — кажется идеальным
местом для пометки на удаление. На практике уборка через меню «Ещё»
(навигация к списку, отбор, выделение, меню, подтверждение, проверка)
занимает больше, и движок обрывает ее:

```
✓ Уведомление-пост с картинкой ... (52.2s)
  ! teardown: timed out after 15000ms
```

Тест зеленый, а тестовый документ остался в базе. Решение: **основная
уборка — последним шагом теста**, `teardown` — только запасной вариант,
если тест упал после записи данных (флаг «уже убрано» на уровне модуля).

### 2. Allure 3 игнорирует `categories.json`

Движок копирует `_allure/categories.json` в результаты, как требует
Allure 2. Allure 3 (`npx allure@3`, без Java) этот файл **не читает**: все
падения попадают в стандартную категорию «Product errors». Категории
Allure 3 берет только из своего конфига (`categories` в `allurerc.mjs`),
старый формат правил (`matchedStatuses`, `messageRegex`) при этом
поддерживается — достаточно подгрузить тот же JSON:

```js
// allurerc.mjs
const categories = JSON.parse(readFileSync(resolve(suiteDir, '_allure', 'categories.json'), 'utf8'));
export default { categories, plugins: { awesome: { options: { singleFile: true, reportLanguage: 'ru' } } } };
```

Проверено: падение `clickElement: "..." not found` после этого попадает в
свою категорию «Элемент не найден».

### 3. Отчет Allure по `file://` — пустая страница

Обычный отчет Allure 3 — папка с данными, которые страница подгружает
запросами; открытая двойным кликом (`file://`), она показывает вечный
индикатор загрузки: браузер блокирует такие запросы. Нужен либо сервер
(`allure open`), либо **`singleFile: true`** в настройках плагина `awesome` —
тогда отчет — один `index.html` (~3,5 МБ) со всеми данными внутри, его
можно открыть и переслать как файл. Там же `reportLanguage: 'ru'`.

### 4. `environment.properties`: обратный слэш съедается

Сведения о стенде (база, URL, платформа, коммит) пишутся в
`_allure/environment.properties`. Это формат `.properties`, где `\` —
экранирование: путь `C:\Program Files\1cv8\...` в отчете превращается в
`C:Program Files1cv8...`. Писать пути прямыми слэшами.

### 5. Один формат отчета за прогон

`--format` принимает одно значение: `json` (по умолчанию, с `--report=путь`),
`junit` или `allure`. Для человека удобнее Allure, для разбора агентом —
JSON; человекочитаемая сводка печатается в stdout в любом режиме (последняя
строка — итог), ее стоит сохранять в файл рядом с отчетом.

## Подготовка стенда (`_hooks.mjs`)

`prepare()` выполняется один раз до браузера и без лимита времени. Минимум,
который окупается сразу, — проверить, что публикация отвечает: иначе каждый
тест упадет с собственной невнятной ошибкой, а так — одна понятная до
запуска браузера. Восстановление базы из эталона (`.dt`) и публикацию тоже
делают здесь, с флагом через аргументы после `--`
(`test <набор> -- --rebuild-stand`), — но только на отдельной тестовой
базе: на рабочей копии это уничтожит данные.

## Разбор падений

Отчет по упавшему тесту: какой шаг упал, сообщение (у `clickElement` — со
списком реально доступных кнопок формы), скриншот момента падения. Каждое
падение отнести к одному из классов:

1. **Ошибка теста** — сменилась подпись, неверное ожидание → править тест.
2. **Ошибка приложения** — то, ради чего регресс существует → в задачу, со
   шагом и скриншотом.
3. **Нестабильность стенда** — публикация не ответила, нет лицензии → чинить
   подготовку стенда, а не тест.

Не «подкручивать» ожидание под текущее поведение, не разобравшись: так
маскируется настоящий баг.

## Как это устроено в наборе

- `gui-test.ps1 -Regress` передает `--url` из профиля базы, пишет
  `_allure/environment.properties` (база, URL, платформа, коммит, время) и
  сохраняет человекочитаемую сводку в `run-output.txt`.
- `-Allure` собирает отчет через `npx allure@3` с конфигом
  [`tests/_lib/allurerc.mjs`](../tests/_lib/allurerc.mjs): один файл, русский
  язык, категории из `_allure/categories.json` набора.
- Общий `prepare()` — [`tests/_lib/stand.mjs`](../tests/_lib/stand.mjs),
  заготовка набора для `-Init` — [`tests/_lib/suite-template/`](../tests/_lib/suite-template/).
- Документация движка: [skills/web-test/regress.md](../skills/web-test/regress.md).
