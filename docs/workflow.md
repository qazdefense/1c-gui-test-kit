# Сценарий пишется вместе с доработкой

Главная идея набора: GUI-тест — не отдельный проект «когда-нибудь потом»,
а часть той же задачи, что и сама доработка. Кто сделал форму или команду,
тот сразу описывает, как пользователь ею пользуется, и прогоняет это
описание в живой базе.

## Цикл

```
доработка ──► сценарий ──► прогон ──► красный? ──► правка кода или сценария
    ▲                                    │
    └──────────── зеленый ◄──────────────┘  ──► сценарий остается в наборе базы
```

1. **Доработка.** Код, форма, команда — как обычно, с обновлением базы.
2. **Разведка.** Открыть новую форму живьем и посмотреть реальные имена:

   ```js
   await navigateLink('Документ.МойДокумент');
   await clickElement('Создать');
   const f = await getFormState();
   console.log(JSON.stringify({ title: f.title, fields: f.fields.map(x => x.name), buttons: f.buttons.map(x => x.name) }));
   writeFileSync('recon.png', await screenshot());
   ```

   Имена в 1С часто не те, что кажутся: «Загрузить...» с многоточием, «Ещё»
   через ё, подпись кнопки не совпадает с именем команды.
3. **Сценарий.** Пользовательский путь от начала до результата
   ([пример](../scenarios/examples/web/post-with-image.js)): что ввели →
   что нажали → **что изменилось**. Каждая проверка — `fail()` с фактическим
   значением.
4. **Прогон.** `.\gui-test.ps1 -Base <база> -Web -ScriptPath <сценарий>`.
   Упал — в папке артефактов `result.json` (шаг, ошибки 1С, состояние
   формы) и скриншот момента ошибки.
5. **Набор.** Зеленый сценарий кладется в `scenarios/<база>/` и дальше
   гоняется вместе с остальными: `.\gui-test.ps1 -Base <база> -Web -Suite scenarios\<база>`.
   Так доработка следующего месяца не ломает тихо доработку этого.

## Что считается тестом, а что нет

| Не тест | Тест |
|---|---|
| форма открылась | после заполнения и записи поле содержит введенное значение |
| кнопка нажалась | после «Загрузить...» в поле появился файл, в предпросмотре — отрисованная картинка |
| документ провелся без ошибки | проведенный документ виден в списке с нужными реквизитами |
| отчет сформировался | в отчете есть ожидаемая строка / итог совпал с контрольным |

## Данные теста

Сценарий пишет в настоящую базу. Правила:

- уникальные значения на каждый прогон (время в заголовке), чтобы прогоны
  не мешали друг другу и строку можно было найти отбором;
- в конце — уборка: `markForDeletion(...)`. Пометка обратима, физически
  удаляет только регламентное «Удаление помеченных объектов»;
- для набора регрессии лучше отдельная тестовая база, а не рабочая копия
  с реальными данными: скриншоты артефактов содержат все, что было на экране.

## Если сценарий пишет ИИ-агент

Набор задуман так, чтобы разработку и проверку мог делать агент (Claude
Code, Codex, Gemini и т.п.) — он пишет код, пишет сценарий и сам «кликает»
в базе. Фрагмент для инструкций агента (`CLAUDE.md` / `AGENTS.md`):

```markdown
## Проверка доработок в интерфейсе 1С

После доработки формы или команды проверь ее в живой базе, а не только по коду:
1. Разведка: getFormState() + скриншот новой формы, выпиши реальные имена полей и кнопок.
2. Сценарий в scenarios/<база>/<задача>.js: пользовательский путь до результата,
   каждая проверка — fail() с фактическим значением. Хелперы (uploadFile,
   findListRow, markForDeletion, assertImageRendered...) — docs/recipes.md.
3. Прогон: .\gui-test.ps1 -Base <база> -Web -ScriptPath <сценарий>
   (без публикации: -ScenarioPath <json> для толстого клиента).
4. В отчете: зеленый/красный, что именно проверено, путь к папке артефактов.
   Красный — сначала result.json и скриншот ошибки, не больше двух попыток
   одного действия; не нашлось — сообщи, а не перебирай варианты.
5. Созданные тестом данные помечай на удаление.
Грабли веб-клиента 1С (iframe HTML-полей, свой диалог выбора файла,
латинское OK, пагинация списков) — docs/gotchas.md.
```

Практика показала, что без такой инструкции агент на вопрос «проверишь
в интерфейсе?» честно отвечает «скорее всего нет» — возможность есть, но
он о ней не знает.
